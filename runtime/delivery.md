# Product Delivery Runtime

The delivery loop is an explicit, opt-in handoff from Discovery to a working local product. It is intended for websites, apps, and internal tools. A request to analyze, explore, or specify a product remains a Discovery task; do not start implementation unless the user asks for a working product.

The current runtime targets macOS and Linux (POSIX file locking and process groups). Product launch and acceptance commands run as local child processes, not inside a security sandbox. The Codex adapter applies Codex CLI sandbox flags to agent invocations; with `--executor handoff`, the host is responsible for the dispatched agent's permissions. Acceptance commands still run locally, so use a trusted workspace and review the planned commands.

## Bounded local loop

`discovery deliver` sends the wish and optional brief through one selected executor. The default `--executor codex` uses the local Codex CLI to plan, build, run the product, check acceptance criteria, and support bounded repair/review attempts. It inherits the CLI's configured model unless `--model` or `--reasoning-effort` explicitly overrides it; there is no silent model substitution. The default attempt limit is three.

`--max-attempts` sets the delivery/repair attempt cap for the current revision (1–20); a resume that archives the prior revision and starts a new generation may set a lower cap than the archived attempt count, but without that reset it cannot be below attempts already used in the current revision.

In a host app that can dispatch subagents, use `--executor handoff` instead. Each plan/build/review call creates a unique request directory under its delivery log folder and prints `request.json`'s path to stderr. The request includes its id, phase, prompt, product workspace, JSON schema, unique `response_path`, requested model, reasoning effort, `owner_pid`, `created_at` and `expires_at` (Unix epoch seconds), and pending status. A host/agent should dispatch a fresh subagent with that requested model and effort, have it follow the prompt within the supplied product scope, then write a schema-conforming JSON object atomically to `response_path` (write a temporary file in the same directory, then rename it). The executor polls for at most `--executor-timeout` seconds and records completed, invalid, timed_out, or cancelled status in that request. Responses are never reused. The Python adapter does not dispatch agents or silently substitute models; that remains the host's responsibility.

Treat the exact printed request path and `id` as the request handle. Before dispatching and again before writing a response, the host should re-read that request and verify its `id`, `response_path`, pending status, and `owner_pid` against the tracked handle and active controller process; pending status alone does not prove that work is still current. Revalidate the owner process using the host's process handle or platform process check, and correlate it with the same path/id because PIDs can be reused. When a new `delivery-resume` has acquired the exclusive workspace lock, it marks leftover pending requests under `.delivery` as abandoned without deleting their request, response, or log files. This lock-based cleanup does not terminate a host-dispatched child; the host remains responsible for cancelling obsolete work and must not publish a response after revalidation fails. A response-read timeout or failure by itself never marks a live request abandoned.

Delivery controller state is stored in `<workspace>/.delivery/state.yaml`; product files live in `<workspace>/product`. A run can stop as `needs_input`, `blocked`, `budget_exhausted`, or `interrupted` without claiming success. Use `delivery-resume` to answer the current question, provide feedback, or continue after a stop. `delivery-status` reads the saved result.

Local build authorization does not by itself authorize changing a core workflow that depends on live external access that is unavailable or not explicitly authorized, or on an external action the local loop cannot perform (such as a real payment or sending a message). Planning pauses for user input and offers one safe alternative; a mock, synthetic demo, manual procedure, or unsent draft is not treated as equivalent unless the user accepts it. If the user already chose an offline/mock/draft version, it can be planned directly. When that live core dependency remains blocked and the user already rejected the alternative or said not to ask again, do not repeat it or ask a new question; keep `needs_input` with a null plan and use the required question field only to state the unresolved blocker, without implying the external action occurred.

The delivered product is local only: no publishing, production deployment, or external release is performed. The host copies product source into a unique verification directory, excluding normal mutable data and caches. Before each acceptance command, it starts a fresh foreground server from that copy on loopback, runs the command there, then stops the server. Commands use `PORT` or the planned `{port}` argument and must not manage their own server. All checks in one run share the copy's `.delivery-data/acceptance` through `DELIVERY_DATA_DIR`, allowing persistence checks across restarts. Even relative fallback writes by an app ignoring the environment variable stay in the copy. Installed `node_modules` and `.venv` directories are linked for reuse; this remains trusted local execution, not protection against arbitrary absolute-path writes or dependency mutation.

Acceptance checks may use different browser origins because each check gets a fresh port. Do not expect browser-local storage to carry between checks; verify it by closing and reopening at the same origin within one check. This is separate from server-side fixtures in `DELIVERY_DATA_DIR`, which intentionally persist across checks. Normal `delivery-preview` runs pin a port per launch scheme and hostname in `.delivery/state.yaml`, so returning to the same preview origin in the same browser profile can reuse client-side data. A saved port that is occupied or invalid causes preview to fail rather than move data silently. Changing the launch hostname creates a separate browser origin; the runtime warns and does not migrate data between origins.

Startup readiness sends HTTP GET to the planned launch URL and requires a direct 2xx response before acceptance runs. For an API-only product, a side-effect-free JSON health endpoint is sufficient; no webpage is required. A POST-only endpoint is not a readiness URL.

For a core user-visible interaction or presentation, when a usable local browser tool is available, acceptance should include at least one real browser user action with visible DOM evidence; static markers or API checks may supplement but not replace it. This does not require browser checks for every criterion or for API-only/static deliverables. If no suitable tool is available, record that UI end-to-end evidence is unavailable rather than claiming it passed.

Replanning retains the latest delivered acceptance baseline by default. To replace or remove a delivered criterion, the plan must name its ID in `superseded_acceptance` with a reason grounded in user feedback for the current revision; old feedback from completed revisions cannot authorize a technical-only change. The independent reviewer receives that declaration and checks the justification.

When an unshipped plan contains a technical error (for example, acceptance fixtures depend on a parent folder absent from the verification copy), use `delivery-resume --replan-reason "<observed error>"`. The reason is recorded separately from user feedback, the old proposal/logs are preserved, and the original wish remains unchanged. Only never-delivered proposal details can be freely corrected: requirements from the latest delivered baseline remain protected. Acceptance fixtures should be embedded in check commands and written under `DELIVERY_DATA_DIR`.

Delivery fingerprints the contents and permission bits of every product file except `.git`, `node_modules`, `.venv`, `__pycache__`, `.pytest_cache`, `.pyc` and `.DS_Store` files, and `.delivery-data`. It checks both the source and verification copy for drift. This detects source and test-file changes, including a launch script losing execute permission, but not dependency or environment drift. Completed verification's loopback URL is historical evidence, not a live server. The foreground `delivery-preview` CLI starts its own server, prints the live URL, and treats Ctrl-C or a single SIGTERM as a clean stop; it uses the app's normal `.delivery-data`, not the isolated acceptance data.

Snapshotting rejects non-regular product files before reading them.
