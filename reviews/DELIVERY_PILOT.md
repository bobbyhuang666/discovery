# Local product delivery pilots

Updated: 2026-10-25. These are author-constructed development evaluations, not a real-user study or a general success-rate claim.

## Scope and execution

The pilot wish was a single-user local customer-followup tool: record customers and conversations, set the next contact date, see today's contacts, and retain data after refresh/restart.

The runtime used the host handoff adapter with fresh GPT-6 Luna agents at maximum reasoning for planning, construction and independent review. The standalone Codex CLI adapter has subprocess integration coverage, but this account's CLI rejected the requested model; no different model was silently substituted.

The generated product uses Python's standard-library HTTP server, SQLite and a Chinese browser interface. It runs locally and was not published.

## Observed loop

1. Initial planning exposed ambiguity in the host contract: a launcher using the supplied `PORT` environment variable was rejected. The contract was corrected to accept environment-based launchers while requiring a loopback URL with an assigned port.
2. The host lifecycle was made explicit: it restarts the server before each acceptance check. Checks share isolated `DELIVERY_DATA_DIR`, allowing a real persistence check without changing normal user data.
3. A construction run was interrupted. Resume reused the existing product files and continued the task.
4. Frozen HTTP acceptance failed because customer IDs were numeric while the accepted interface checks used string IDs. Construction was not treated as delivery. The next build corrected serialization and a today/overdue badge defect.
5. The host ran all frozen checks successfully. A fresh reviewer independently exercised the API and Chrome UI and returned a passing verdict. Only then did the controller transition to `delivered`.

## Evidence inspected

- Actual HTTP creation, conversation recording and detail retrieval.
- New server processes/ports between creation and retrieval, with retained SQLite data.
- Today/future/overdue filtering, date ordering and invalid-input rejection without inserting invalid records.
- Real Chrome interaction: create a customer, record a conversation, reload, reschedule, edit profile, and inspect desktop/mobile layouts.
- No browser runtime errors during the observed workflow; no horizontal overflow at a 390px viewport.
- Durable per-attempt check logs, source fingerprints and the independent review response in the pilot workspace's `.delivery` directory.

## Second scenario: purchase CSV merge

The second authored wish requested a local upload/preview/download tool that merges purchase CSV files by order number, keeping the latest valid date and showing rejected rows with source context. It did not request accounts, external services or durable storage of uploaded business data.

The first acceptance proposal incorrectly read fixtures from the product's parent directory, which does not exist in the isolated verification copy. Construction was interrupted rather than treating that infrastructure mistake as a product success. A technical replan preserved the original wish and product edits, archived the never-delivered proposal, and embedded disposable fixtures in the checks under `DELIVERY_DATA_DIR`.

The rebuilt proposal passed both frozen host checks in a staged source copy. These checks drove real browser uploads, parsed actual downloaded CSV files, checked exact winning rows and invalid-row reasons, and performed a second merge without refreshing. A fresh independent reviewer also used system Chrome, reversed file order to verify same-date tie handling, checked reordered columns, and tested empty and missing-header files. Read-only review confirmed loopback binding and memory-only upload handling.

The controller reached `delivered` at `pilots/purchase-merge/.delivery/revision-2/attempt-1`. Its independent response is `review/review-4o42zkkb/response.json`; source fingerprint status was confirmed current. Product artifacts are `app.py` and `README.md`.

This failure also led to an explicit `--replan-reason` path. Technical notes are separate from product feedback, and only current-revision user feedback may authorize superseding a delivered acceptance criterion. Historical feedback, blank feedback and arbitrary post-delivery answers cannot supply that authority. At that stage the runtime suite passed 78 tests; an independent focused review passed seven authorization/resume tests and a separate feedback → question → answer reproduction.

## Fourth scenario: browser-only task list

The fourth authored wish requested add/complete/rename/delete operations, correction of blank input, mobile usability and persistent task data without an account or backend storage. A first never-delivered check incorrectly expected one browser origin's storage to appear at the next check's different port. The controller was interrupted before any builder was dispatched; a technical replan kept the product requirement and made each origin-dependent test self-contained.

The controller reached `delivered` at `pilots/browser-tasks/.delivery/revision-2/attempt-1`; the review response is `review/review-04xueoo2/response.json`.

The scenario also exposed a separate runtime defect: ordinary preview restarts chose different ports, making client-side data appear absent in the same browser profile. Preview ports are now persisted per launch scheme and hostname, while acceptance ports remain ephemeral. Independent review rejected the first fix because macOS allowed a specific-address `SO_REUSEADDR` bind probe alongside an existing wildcard listener, after which readiness HTTP reached the wrong service. The corrected preflight uses a short TCP connection and refuses known occupied ports before product launch, readiness HTTP, a URL or fallback. This does contact a listener at transport level; it sends no HTTP request and is not a security-sandbox claim. A narrow preflight-to-bind race remains with generic launch commands.

The corrected runtime passed 82 tests and an independent real CLI wildcard-listener recheck plus a two-start persistent-profile probe. Product-level `browser-qa.py` then drove two ordinary preview CLI runs at the same URL, with a temporary browser profile: the renamed/completed task survived, the explicitly deleted task stayed absent, and a fresh profile saw no tasks. Its `.delivery/browser-qa/result.json` and desktop/mobile screenshots record no JavaScript errors, unexpected network requests or horizontal overflow; owned test previews exited cleanly. Status remained `delivered` with the current product fingerprint.

Changing the launch hostname intentionally uses a separate browser origin and warns that data is not migrated; prior hostname-port mappings are retained. Clearing browser site data or changing browser profiles remains outside the persistence guarantee.
